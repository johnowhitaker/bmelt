# Normal-Mode Code-Execution Hook Plan - 2026-05-06

## Why The Last Hook Wedged

The Drive #3 timing hook patched the visible resident call site:

```text
0x41de  LCALL 0x002e
0x41e1  JNC   0x422f
```

That looked like a good place to prove normal-mode execution, because
`0x002e` is the visible CDD/materializer parser. The no-delay marker variant
programmed cleanly, but a later delay variant made the drive stop enumerating
as a PLDS optical LUN after cold boot.

Raw 8051 assembly explains why. `0x41de` is not a quiet post-setup callback.
It sits in the middle of `FUN_CODE_40b2`:

```text
0x40b2  CDD/container setup path
0x40e2  read controller 00:0000 through 0x4091..0x4098
0x410a  check "LITE"
0x415b  check descriptor base == 0x00007000
0x4178  check parser window == 0x00004000
0x4180  FUN_CODE_1009(5)
0x4185  copy descriptor fields into 0x8248..0x8255
0x41de  FUN_CODE_002e
0x41e3  restore 0x4023 from 0x80b0
0x41eb  FUN_CODE_1009(5)
0x41f2  FUN_CODE_141e(0)
0x4220  if continuation required: FUN_CODE_111a(2)
0x422c  clear A/PSW and return
```

So the delay ran before controller shadow restore and before the possible
`FUN_CODE_111a(2)` continuation. It likely tripped a boot/controller watchdog
or left a transaction half serviced for too long. This is useful evidence that
the path is live, but it is too early for blocking work.

## Safer Next Hook Shape

The next fresh-drive hook should not run inside the `0x002e` transaction. It
should run after the `0x40b2` continuation has completed, and it should be a
single quick side effect, not a delay.

I prepared three offline candidate families:

```text
references/firmware/extracted/helper-bypass-candidates/post-materializer-ret-marker-074030/
references/firmware/extracted/helper-bypass-candidates/post-materializer-ret-marker-074030-restore/
references/firmware/extracted/helper-bypass-candidates/post-materializer-runtime-bridge-clamp07/
references/firmware/extracted/helper-bypass-candidates/post-materializer-runtime-bridge-clamp07-restore/
references/firmware/extracted/helper-bypass-candidates/post-40b2-caller-marker-074030/
references/firmware/extracted/helper-bypass-candidates/post-40b2-caller-marker-074030-restore/
```

They are generated by:

```text
scripts/build_liteon_post_materializer_hook_candidates.py
```

No drive commands were sent while building them.

### Preferred Candidate

`post-materializer-ret-marker-074030` patches only the `FUN_CODE_40b2` return
epilogue:

```text
0x422c: e4 f5 d0    -> 12 6e e3
0x422f: 22          remains the original RET
```

The cave at `0x6ee3` writes one byte:

```text
controller/public 0x074030 = 0x5a
```

Then it executes the stock return state:

```text
CLR A
MOV PSW,A
RET
```

Control returns to the original `0x422f` RET, so the surrounding function exits
normally. This is the least bad follow-up because it runs after the fragile
`0x40b2` continuation instead of inside it.

Expected observable if successful:

```text
normal READ BUFFER mode=1 id=01 offset=0x074000 length=0x80
byte +0x30 changes from 0xff to 0x5a
```

If this still shows `0xff`, the write either happens too early and is
overwritten, `0x074030` is not a valid write alias from this context, or
`0x40b2` does not run in the normal path being observed.

### Better Candidate: Runtime Bridge RAM Patch

The stronger follow-up is `post-materializer-runtime-bridge-clamp07`. It uses
the same late `0x422c` resident hook, but instead of writing a free-standing
marker byte, it writes into the already materialized normal response bridge.

The known normal bridge chunk appears at public offsets `0x077100`,
`0x077140`, and `0x077180`. Its response-offset clamp includes this pattern:

```text
... 90 8a 4c e0 c3 94 0e 40 08 90 40 11 74 0e f0 ...
```

The first `0x0e` is the compare threshold; the second `0x0e` is the value
written to controller register `0x4011` when the high offset byte is clamped.
The candidate changes the second immediate to `0x07` in the six most common
observed rotating slots:

```text
0x077156: 0x0e -> 0x07
0x077196: 0x0e -> 0x07
0x0770e6: 0x0e -> 0x07
0x077026: 0x0e -> 0x07
0x0770a6: 0x0e -> 0x07
0x077066: 0x0e -> 0x07
```

This is the most interesting next test because it is not a CDD source
mutation. It asks whether the visible resident, after the materializer has
run, can patch the materialized normal runtime code in RAM. If it works, a
high-offset `READ BUFFER id=01` probe should return a different direct SCSI
response, while ordinary `0x070000..0x07ffff` reads should remain stock.

Suggested live proof shape:

```text
baseline A: READ BUFFER id=01 offset=0x070000 len=0x80
baseline B: READ BUFFER id=01 offset=0x077000 len=0x200
baseline C: READ BUFFER id=01 offset=0x0f0000 len=0x200
install candidate and cold boot
patched A:  READ BUFFER id=01 offset=0x070000 len=0x80  (should stay stock)
patched B:  READ BUFFER id=01 offset=0x077000 len=0x200  (may show 74 07 f0 if hook lands and bridge slot is visible)
patched C:  READ BUFFER id=01 offset=0x0f0000 len=0x200  (should change if clamp affects direct response)
restore stock resident and cold boot
restore C:  READ BUFFER id=01 offset=0x0f0000 len=0x200  (should match baseline again)
```

The read-only helper for those captures is:

```text
scripts/probe_liteon_materialized_bridge_clamp_effect.py
```

Example:

```text
python3 scripts/probe_liteon_materialized_bridge_clamp_effect.py \
  --device /dev/sg0 \
  --out-dir references/evidence/live/<run-name> \
  --label baseline
```

Static slot validation is recorded here:

```text
analysis/8051/materialized-bridge-clamp-slots-20260506.md
```

That scan found the exact bridge clamp pattern in `3934` saved capture
instances across `1967` files. The six addresses in the candidate cover the top
six rotating clamp-immediate slots.

The guarded end-to-end live wrapper is:

```text
scripts/run_liteon_materialized_bridge_clamp_live_test.py
```

It is dry-run by default and refuses the write path unless `sg_inq` reports a
PLDS DS-8ABSH optical LUN. With `--execute`, it performs:

```text
baseline probe -> install candidate -> Pico cold boot -> patched probe
-> install restore -> Pico cold boot -> restored probe
```

The wrapper also counts the stock clamp pattern in baseline `0x077000`
captures and refuses the install if the target bridge chunk is not visible,
unless `--allow-no-baseline-clamp-hit` is passed deliberately.

If this lands, it is a real bridge over the CDD wall: a resident-prefix hook
can modify decoded/materialized normal code without knowing how to encode the
CDD source.

### Higher-Risk Candidate

`post-40b2-caller-marker-074030` patches the caller:

```text
0x26fb: LCALL 0x40b2 -> LCALL 0x6ee3
```

The cave calls original `0x40b2`, preserves PSW/ACC/DPTR, writes the same
public marker, restores state, and returns. This may run later or more often in
the service loop. That gives it a better chance of writing after normal runtime
has settled, but a worse chance of being harmless. Keep it second.

## Live Test Rules

Do not run any candidate while the drive enumerates as `Generic External`.
The PLDS optical/currentboot LUN must be visible first.

For a fresh or recovered PLDS-visible drive:

1. Capture stock identity and `READ BUFFER id=01 offset=0x074000`.
2. Also capture `READ BUFFER id=01 offset=0x070000`, `0x077000`, and
   `0x0f0000`.
3. Prefer `post-materializer-runtime-bridge-clamp07` if the high-offset
   baseline is stable; otherwise run `post-materializer-ret-marker-074030`.
4. Cold-cycle with Pico.
5. Recheck identity and the same READ BUFFER windows.
6. If any direct response changes, immediately run the matching restore
   candidate and retest stock after a cold boot.
7. If the drive fails to enumerate, do not try the caller variant on that
   drive.

The return-epilogue candidates are still boot-path code patches, so the risk
is not zero. The improvement is that they avoid delaying the materializer
itself. The runtime bridge patch has a better proof signal than the marker but
also touches normal decoded code, so it should only be used on a PLDS-visible
fresh/recovered drive with a restore candidate ready.

Previous marker-only sequence, if used:

1. Run `post-materializer-ret-marker-074030`.
2. Cold-cycle with Pico.
3. Recheck identity and `READ BUFFER id=01 offset=0x074000`.
4. If the marker appears, immediately run the matching restore candidate and
   retest stock.
5. If the drive fails to enumerate, do not try the caller variant on that drive.

## Runtime Code Surface To Study In Parallel

The selector-22 materialized image at:

```text
analysis/8051/drive3-selector22-runtime-image-0000-3fff-20260506.bin
```

is a real 16 KiB 8051-looking runtime image stitched from the currentboot CDD
oracle. Useful anchor points:

```text
0x1406  likely READ BUFFER mode=1 handler:
        checks xdata[0x8a4c] == 0x01 and length at 0x8a51..0x8a54

0x17eb  READ/READ-like handler:
        checks xdata[0x8a49] == 0x28 or 0xa8

0x3661  broader packet dispatcher:
        checks xdata[0x8a49] against 0x28, 0xa8, 0xbe, 0xd5, 0xb9,
        then uses controller/status paths

0x33cf  mechanics-state reset/config:
        clears 0x4860..0x4864, writes 0x4867 = 0x61, clears 0x486a..0x486b
```

These are not directly patchable yet because they come from encoded CDD
runtime material. The bridge from the resident hook to a real oracle is to use
a safe resident-prefix hook to write or alter state after materialization, then
observe these normal handlers through public `READ BUFFER` or normal command
responses.
